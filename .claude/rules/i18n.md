# i18n

User-visible text is translated with next-intl into the locales `lib/i18n/routing.ts` lists. `zh` is both the default locale, shown when a visitor's language is unknown, and the source locale, which new text is written in and every other locale is translated from.

## What gets translated

- Everything a user sees or hears: JSX text, `aria-label` and other accessible names, `title`, `placeholder`, `alt`, toasts, validation and error messages, and `metadata`.
- Not translated: user and backend content such as task names and comments, and `ApiError.message` and other developer-facing logs and thrown errors.

ESLint's `i18next/no-literal-string` checks only JSX text and some attributes. Route text outside JSX, such as toasts, `metadata`, and labels in constants, through `t()` all the same.

## Writing text

Translate every locale yourself, in the same change as the code:

1. Render the text with `t()` (see "Reading messages"). Translate whole sentences, with values, plurals, and rich text in ICU syntax, such as `{count, plural, other {# tasks}}`, and their values passed to `t()`.
2. Write the source-locale text in `messages/zh/{namespace}.json`, then the finished translation in the same file under every other `messages/{locale}/`.
3. Follow `messages/terms.json`: a term under `keep` stays as written in every locale; a term under `translations` uses the listed translation. Add a term when the same word must read the same way across the product.
4. Changing source-locale text means translating it again in every locale. Removing code removes its keys from every locale; nothing reports unused keys.
5. Run `pnpm test messages/messages.test.ts` until it passes.

## Namespaces and keys

- One namespace per owner, one file per namespace: a feature's directory name (`demo-task`), `app` for text in `app/`, and `ui` for `components/` and `components/ui/`. Text in `app/` nests by route, such as `demos.tasks.title`.
- A new namespace needs its file in every locale, holding its keys without a namespace wrapper, and an entry in both `Messages` and `NAMESPACES` in `lib/i18n/messages.ts`.
- Code uses only its own owner's namespace. To show another feature's text, render that feature's component through its public entry.
- Keys are camelCase, nested by component or area and then by meaning: `taskList.emptyTitle`, `errors.nameTaken`. Name a key after what the text means; the same words with different meanings get separate keys.

## Reading messages

| Where | How |
| --- | --- |
| Server Component | `useTranslations(namespace)`, or `await getTranslations(namespace)` in an async one |
| `generateMetadata` | `await getTranslations(namespace)` |
| Client Component | `useTranslations(namespace)`, with the namespace sent by `ClientMessages` (below) |
| Server Action, Route Handler | `await getTranslations({ locale, namespace })`. They can't read root params, so the caller passes `locale` from `useLocale()`, a mutation as an options factory argument; `lib/i18n/request.ts` rejects unsupported values |
| Code outside React, such as a `QueryClient` callback | Render a component that calls the hook, as `RequestErrorMessage` in `app/providers.tsx` does |

Client Components receive only the namespaces their route sends, from `lib/i18n/client-messages.tsx`:

- The root layout wraps its content in `<RootClientMessages namespaces={["app", "ui"]}>`, which also gives Client Components the locale and time zone.
- Below it, a layout, template, or page adds namespaces for what it renders with `<ClientMessages namespaces={[…]}>`. Each one lists only what it adds; the messages sent above it stay available. Add one where a subtree needs namespaces its siblings don't: in the layout of a feature's routes, or in a page for a namespace only that page uses.

ESLint's `i18n/client-namespaces` checks each list against the Client Components it encloses, and `pnpm lint --fix` rewrites it.

## Validation and API errors

- A zod schema whose messages users see is a factory that takes `t`, such as `createTaskNameSchema(t)`. Forms build it with `useTranslations` inside `useMemo`; a Server Action builds it from `getTranslations({ locale, namespace })`.
- Show an `ApiError` with copy from the owning feature's namespace, chosen by `error.code` or `error.status`, and pass `error.params` to `t()` ([data-fetching.md](data-fetching.md#errors-in-react-queryowned-data)).

## Dates and numbers

Show a moment in time with `<DateTime value={…} format={…} />` from `components/date-time.tsx`, which renders it in the computer's time zone once the page has hydrated: only the browser knows that time zone. ESLint enforces it.

- Anything else whose result depends on the time zone, such as grouping by day or telling whether a moment is today, also runs in the browser after hydration.
- A calendar date without a time, such as a due date, is not a moment: show it as the date it is, since converting it through a time zone can move it to the day before or after.
- Format relative times ("3 minutes ago") and numbers, which don't depend on the time zone, with next-intl's `useFormatter()` or `getFormatter()`.

## URLs and navigation

URLs carry no locale: `proxy.ts` shows each visitor their own language at the same URL. Link and navigate with `next/link` and `next/navigation`, using plain paths such as `/demos/tasks`.

A visitor picks a locale with `components/locale-switcher`, whose links put the target locale in front of the current path (`/en/...`) for `proxy.ts` to record. Any other language control links the same way.

## Adding a locale

Add it to `routing.locales` in `lib/i18n/routing.ts`, create `messages/{locale}/` with every namespace file translated, add its translation to each entry in `messages/terms.json`, and run the messages test.
