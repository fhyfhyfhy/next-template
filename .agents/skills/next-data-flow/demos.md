# Data demo

The Data demo under `/demos` is the runnable reference for this skill and its rules: a small Demo task app on the template's full-stack shape ([ADR 0003](../../../docs/adr/0003-fullstack-demo-backend.md)). Server code calls the features' server data layer directly; the browser reads through `fetchApi` from Route Handlers under `/api/demo` and writes through Server Actions; data lives in Postgres and files in S3-compatible object storage ([ADR 0004](../../../docs/adr/0004-demo-uploads-presigned-object-storage.md)). Before writing a pattern listed below, read its code and spec; adapt names and keys to the real feature, and keep its owner choice only if the same signal applies.

- Run it with `pnpm demo:dev`, or `pnpm demo:build` then `pnpm demo:start` for production behavior. These scripts start Postgres and the object storage from `compose.demo.yaml` (Docker required), migrate the Demo database, and enable the Demo backend; under `pnpm dev`, `build`, and `start` it stays off, the Data demo pages render a notice, and `/api/demo` answers 404.
- Code lives in `app/[locale]/demos/(data)/` (routes), `app/api/demo/` (Route Handlers), `features/demo-task/`, and `features/demo-upload/` (paths below are relative to `features/demo-task/` unless they start with `app/`, `e2e/`, `features/`, `lib/`, or `scripts/`). The control endpoints under `/api/demo/control/*` reset data, pause or step the Demo 生成器, inject faults into data-layer operations, and list data-layer calls.
- `pnpm demo:test:e2e` runs the specs in `e2e/demo/` serially against its own production build in `.next-demo-e2e` on port 3999 (`DEMO_E2E_PORT`), on the `e2e` dataset (its own database and bucket), so a running `demo:dev` or `demo:start` is left alone; each test resets that dataset first. `pnpm test:e2e` is for the project's own specs and skips them. `pnpm demo:test` runs the data-layer tests (`*.db.test.ts`) against the same services on the `test` dataset.

| Page | Owner | Why |
| --- | --- | --- |
| `/demos/tasks` | Server Component | Filters, sort, and page change on navigation; the user's own writes refresh it. A browser poll of the in-progress tasks refreshes it when one of them changes |
| `/demos/tasks/[id]` | React Query | A task advances while the user stays |
| `/demos/feed` | React Query | Infinite scroll; favorites update two components together |
| `/demos/search` | React Query | Re-requested as the user types |
| `/demos/recent` | React Query | Inputs come from `localStorage` |
| `/demos/lab` | React Query | Error-policy experiments |
